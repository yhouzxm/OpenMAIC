`RepositoryRevision` is an opaque branded string, but the current `repositoryRevision(value)` Port factory checks only nonempty text and the fake emits `fake-1`, `fake-2`, etc. **Final contract:** every RepositoryRevision, including fake/test tokens, is a canonical positive signed-`BIGINT` decimal string in `1..9223372036854775807`. Validate the *entire* string with conceptual grammar `^[1-9][0-9]*$`, then check `BigInt(value) <= 9223372036854775807n`; do not normalize whitespace, sign, exponent, fractional syntax, or leading zero. Accept `"1"`, `"2"`, `"999"`, and the maximum. Reject `""`, whitespace, `"0"`, `"-1"`, `"+1"`, `"01"`, `"1.0"`, `"1e3"`, `"fake-1"`, and above-maximum values. The Port factory must enforce this in 1B-4B; the PostgreSQL adapter additionally validates every incoming/outgoing DB representation and fails closed on persisted drift. Parsing uses `BigInt` for validation only; the Port and mapper return/store a string, never JS `Number`. Do not use `xmin` or derive the token from `authorizationVersion`. An invalid candidate token is rejected before SQL; a malformed stored token is a sanitized `INTEGRITY_FAILURE`, not a raw cast error. Revision arithmetic remains database-side (`repository_revision + 1`); equality is exact canonical string equality.

This is **mandatory Port validation strengthening**, not a schema change. In 1B-4B each fake row must start with canonical revision `"1"` and a state-changing save must advance that row's own decimal revision by one; it must not use the current shared `fake-N` sequence as a substitute for per-row CAS. A small test-only numeric counter may remain only where it is independently safe and does not determine a persisted row's revision. Existing `repositoryRevision('wrong-tenant-token')` and `repositoryRevision('x')` test fixtures must become legal but mismatching decimal tokens, such as `"999"`, so tenant-scope tests continue exercising scope rather than failing at parser construction. No Repository method signature changes.

The six different stored aggregate types are not one generic repository: User, Tenant, Membership, RoleGrant children, SystemAdminGrant, and (later) Session have different privileges/lifecycles. Role and Permission remain code-owned, not database repositories.

## 2. Rehydration contract — closure design for 1B1-F02

**Final decision:** rehydration is a **PRIVILEGED PERSISTENCE RECONSTRUCTION API**, not part of the ordinary Application-facing Domain API. In 1B-4B, each entity module may export a narrowly named persistence-only function (conceptually `rehydrateMembershipForPersistence(state)`, and corresponding functions for User, Tenant, RoleGrant, SystemAdminGrant) that can reach its module-private constructor token. A dedicated `lib/zhiban/domain/identity/persistence-rehydration.ts` module may aggregate those sibling functions internally. The exact function names may follow local style, but their role and import path must remain distinct from normal creation/mutation. **Do not add `User.rehydrate`, `Membership.rehydrate`, or any other public static rehydrate method** to a class exported by the standard barrel. `lib/zhiban/domain/identity/index.ts` must export neither these functions nor a persistence snapshot constructor/token. Apart from the aggregator's own sibling imports, only production code under `lib/zhiban/infrastructure/identity/**` may import the privileged path or individual `*ForPersistence` functions; narrowly scoped test imports are allowed solely to verify this boundary. Application, UI, OpenMAIC adapters, and ordinary Domain consumers must not deep-import them. In 1B-4B, an import-boundary architecture test/lint guard must scan imports and re-exports across the repository, reject forbidden direct or indirect exposure (including the standard barrel), and permit only the exact infrastructure/test allowlist. Runtime structural validation remains mandatory for unknown JavaScript-shaped input; persistence-only does not mean unchecked. The mapper must not use `Object.assign`, `Object.create`, reflection, plain casts, or business-command replay.

**Runtime constructor hardening is part of 1B1-F02 closure, not optional TypeScript polish.** Each affected class constructor must require a module-private `Symbol` construction token (or equivalent true runtime gate), checked on every construction. The token is never exported, stored on a public static property, passed through a Port, or given to Infrastructure. Domain-owned fresh factories, persistence-only rehydration functions, and genuinely runtime-private transition primitives in that module are the only paths that may use it. TypeScript `private` alone is erased at runtime. A constructor token by itself is insufficient if a runtime-callable `private changed(...)` can relay that token: Membership's instance-bound `changed`, `check`, and `replacement` paths must be ECMAScript `#private` (or equivalently closure-private where no instance method is exposed); pure stateless validation helpers may remain module-private functions. A public command verifies authentic receiver identity before executing; `#private` access supplies a runtime brand check, so `Object.create(Membership.prototype)`/borrowed public methods throw. `effectiveGrantsAt` must also reject a forged receiver before it can report authorization eligibility. A direct `(object as any).changed(...)`-style call cannot reach an internal transition. Immutable returned instances are issued only from validated paths. Constructor token plus `#private` protect aggregate runtime integrity against ordinary JS caller misuse; the **reachability** of privileged rehydration is controlled separately by the module/import boundary and architecture test. Neither mechanism is a hostile-process sandbox: source-modifying or arbitrary privileged code in the same process can bypass architectural policy.

`RoleGrant` acceptance inside Membership must use an issued-instance check (for example, a module-private `WeakSet` or runtime brand), not `instanceof` alone, because `Object.create(RoleGrant.prototype)` can forge the latter. User/Tenant/RoleGrant/SystemAdminGrant have no current `private changed` helper and need not acquire one. Their public transitions (`disable`/`restore`/`archive`/`revoke` as applicable) and validity getters still reject forged receivers through a runtime brand/issued-instance check; their constructors retain the token gate and their fresh/persistence-only reconstruction paths validate every field. Revocation never clears or rewrites the first `revokedAt`. Production save adapters whitelist/project incoming state and validate it through the privileged Domain reconstruction boundary before comparison or write; they do not accept plain-object casts or prototype-forged aggregates. Do not add an unsafe public construction token or pretend a persistence-only function means trusted input. The specific code and negative tests belong to 1B-4B, not this design revision.

## 3. CAS, absence, and version semantics

Each aggregate row starts with `repository_revision = 1`. A state-changing successful `save` of User/Tenant/SystemAdminGrant/Membership advances its own row revision exactly once by SQL arithmetic and returns the resulting decimal string; `create` returns `"1"`. A **TRUE_NO_OP** performs no UPDATE and returns the **current stored `Loaded<T>`**: canonical persisted aggregate value plus current unchanged revision, not the caller's desired object. A stale caller cannot turn a stale write into success with equal-looking state. The conceptual state-changing update is `UPDATE zhiban_identity.<table> SET ..., repository_revision = repository_revision + 1 WHERE <scoped id> = $id AND repository_revision = $expected::bigint RETURNING repository_revision`. Every dynamic value is parameterized. No dynamic table/schema names; each repository uses fixed, schema-qualified SQL.

### A. Global Aggregate Save Decision Model

This model applies separately to User, Tenant, and SystemAdminGrant. None has `authorizationVersion`; do not add that field, apply Membership's `N/P` test, or introduce a generic aggregate version framework. Each uses its own row and CAS boundary, with fixed schema-qualified SQL and the restricted `CONTROL_RUNTIME` identity.

For each global `save`, the mandatory order is: **(1)** use the correct transaction-scoped `CONTROL_RUNTIME` client and lock the current row with `SELECT ... FOR UPDATE` (or a strictly equivalent same-client lock/CAS protocol); **(2)** return `CONFLICT` if absent; **(3)** compare `expectedRevision` with the locked current RepositoryRevision and return `STALE_WRITE` on mismatch, even when desired and stored states look identical; **(4)** validate aggregate identity, immutable fields, lifecycle/history rules, and reconstructed Domain invariants; **(5)** compare the complete persistence-relevant state; **(6)** if identical, return the **current stored `Loaded<T>`**, including its canonical stored value and unchanged revision, without UPDATE or Repository-generated audit; **(7)** otherwise execute a parameterized state-changing CAS UPDATE with `WHERE id = $id AND repository_revision = $expected::bigint`, check one returned row, and advance `repository_revision` exactly once by database arithmetic; **(8)** if the Application command requires audit, append its event on that same client; **(9)** commit, or roll back the entire transaction on failure. The row lock protects the comparison until commit. A zero-row UPDATE after a locked matching row is an invariant/connection fault, not an automatic stale/not-found classification. Signed `BIGINT` overflow fails closed. The Repository never infers a business audit event from state equality or difference; whether an attempted but no-op Application command requires an event remains a later Application decision.

**Global TRUE_NO_OP** requires the expected repository revision to match, all immutable/lifecycle checks to pass, and the desired *full* persistence state to equal the current stored full state. It has **no authorizationVersion condition**. User state includes `id,status,createdAt,updatedAt,disabledAt,disabledReason`; `id` and `createdAt` never change, and ACTIVE/DISABLED disabled-fact consistency remains enforced. `User.disable` and `User.restore` produce state-changing saves with fresh revisions; a repeated identical snapshot save does not. Tenant state includes `id,code,displayName,status,createdAt,updatedAt,disabledAt,disabledReason`; `id`, stable `code`, and `createdAt` remain immutable, and current Domain commands preserve `displayName`. Existing Domain commands `disable`, `restore`, and `archive` produce state-changing saves with fresh revisions; identical-state saves do not. This does not invent a metadata mutation command. SystemAdminGrant state includes `id,userId,createdAt,validFrom,validUntil,revokedAt`; all fields except `revokedAt` are immutable, and only `NULL → first timestamp` is a legal revocation change. A first revoke advances revision; an identical revoked snapshot does not. Clearing `revokedAt` or changing the first timestamp is `INTEGRITY_FAILURE`, even with a current RepositoryRevision. Global fakes and real adapters must apply the same stale-before-no-op and full-state rules, not unconditional revision generation.

### B. Membership Aggregate Save Decision Model

For Membership `save`, the mandatory decision order remains: **(1)** validate TenantContext/candidate scope, **(2)** read/lock the current scoped parent row inside one transaction (`FOR UPDATE`), **(3)** validate expected RepositoryRevision against the locked current revision, **(4)** validate immutable identity/history and reconstructed Domain invariants, **(5)** validate authorizationVersion and canonical authorization-fact rules, **(6)** compare the *full* persistence-relevant state, **(7)** only then decide TRUE_NO_OP versus state-changing CAS. This is not an unsafe check-then-write: the lock holds until commit and the `WHERE repository_revision` predicate remains the final guard for an UPDATE. If the row is absent in that scope, `save` returns existing Port `CONFLICT` (find returns `null`). If it exists but revision differs, return `STALE_WRITE` **before** no-op detection; a current revision plus auth-version rollback, immutable identity mismatch, or history mutation yields `INTEGRITY_FAILURE` (explicit candidate tenant mismatch: `TENANT_SCOPE_VIOLATION`). A zero-row update after a locked, matching row is an invariant/connection fault, not automatically “not found” or “stale”; rollback and fail closed. No unscoped second SELECT may distinguish nonexistent from RLS-invisible/wrong-tenant rows. Business hard delete is prohibited, which stabilizes absence classification while the row lock is held. Revision overflow at signed `BIGINT` maximum fails closed; it never wraps. Concurrent transaction failures are separately mapped and never leaked as SQL messages.

For Membership, `authorizationVersion` is a **separate Domain business version**, safe integer 0..9007199254740991. Let `P` be persisted and `N` desired authorizationVersion, checked only after scoped parent lock and repository-revision CAS precondition. `N < P` rejects. At `N = P`, canonical authorization facts must be exactly equal or the save rejects with `INTEGRITY_FAILURE`. At `N > P`, either equal or changed canonical facts are allowed, subject to all immutable/history checks. The Repository never sets/increments the Domain version itself. Multiple legitimate Domain commands before one save may yield `N > P + 1`; do not require exactly +1. In particular, existing `Membership.replaceGrants` can legitimately advance the version while ending with equivalent authorization facts. This **version-only advancement is not a persistence no-op**: persist `N` and advance repositoryRevision so prior authorization snapshots become stale. Application audit follows the Domain command meaning, not a Repository comparison of final facts; the Repository never suppresses or invents a `ROLE_GRANTS_REPLACED` audit event.

**Membership TRUE_NO_OP** means both `N = P` and the entire persistence-relevant Domain state (including non-authorization metadata, timestamps, full grant history and order) is unchanged. Comparing only effective or canonical authorization facts is insufficient. After the seven ordered Membership checks above, return the current stored `Loaded<Membership>`—its stored value and same revision—without UPDATE, child write, or revision advance. Do not substitute the caller's equal-looking object. An idempotent repeated `revokeGrant` that returns the same object is the current example. A metadata change with equal auth facts is a write and advances repositoryRevision, not authVersion. This target conflicts with the current fake/contract test, which requires a fresh revision even on identical-state save; §10 records the required Port clarification and contract-test revision rather than pretending the contract already agrees.

The existing Domain `AUTHORIZATION_VERSION_CONFLICT` is raised by a failed business-command precondition, before persistence. It is not a new Port error: a current RepositoryRevision paired with a lower or inconsistent persisted authorization snapshot maps to `INTEGRITY_FAILURE`, while a stale RepositoryRevision maps to `STALE_WRITE`.

**Same-auth-version auth-fact guard:** after parent lock, compare the persisted and proposed canonical authorization projection: Membership `status`, `disabledAt`, `disabledReason`, and the **entire RoleGrant history** (`grantId`, infrastructure `grantOrdinal`, roleCode, scope kind/id, createdAt, validFrom, validUntil, revokedAt), including any other existing Domain field that genuinely changes authorization semantics. Sort by precise `grantOrdinal ASC`, then `grantId ASC`; never rely on natural DB order or unsorted `JSON.stringify`. The ordinal is comparison metadata, not a Domain field; existing grants retain theirs, and new grants receive deterministic append ordinals under the parent lock. At equal versions, any projection difference is `INTEGRITY_FAILURE` before any write. At higher versions, equal projections are explicitly permitted, while grant-history append-only/first-revocation and immutable parent checks still apply. `updatedAt` may change without auth-version change only through a future reviewed metadata operation; current Domain has none. Never compare `authorizationVersion` to the repository token or convert `BIGINT` to JS number.

## 4. Membership/RoleGrant aggregate transaction

Membership is the parent persistence concurrency boundary. All role-grant additions, first revocations, replacements, status changes, reactivation, and rejoin operate under the **same parent lock and expected parent revision**. No repository method or maintenance shortcut may mutate a RoleGrant child alone. Parent revision advances once per successful aggregate save, including child-only changes; the Domain advances authorizationVersion for effective authorization-fact changes. Grant history is append-or-first-revoke only: no DELETE, no role/scope/window edit, no rewriting an earlier `revoked_at`, no grant-ID reuse. Membership rows likewise have no business DELETE. LEFT and DISABLED are retained lifecycle states; rejoin reuses MembershipId and appends freshly approved grant IDs through existing Domain behavior.

Write sequence on one exclusive `TENANT_RUNTIME` client:

1. `BEGIN` at `READ COMMITTED`; set transaction-local tenant context and validate it; no query from another client.
2. `SELECT` the scoped Membership `FOR UPDATE` using **both** `tenant_id = $tenant` and `membership_id = $id` (or `user_id = $user` for lookup). Fail closed on absence; validate the expected parent revision against the current token before considering equal state. Then compare immutable id/userId/tenantId/createdAt and validate the persisted/candidate aggregate.
3. Read all children for that `(tenant_id,membership_id)` with explicit `ORDER BY grant_ordinal, grant_id`; verify contiguous/unique ordinals as chosen below, unique grant IDs, matching parent, and reconstruct a complete history through the privileged function. Compare authorizationVersion/projection and irreversible history **before** full-state/no-op decision. The parent lock is the serialization point because **every formal Repository child writer** must take it; child `FOR UPDATE` is unnecessary for that path. The current DB ACL may permit a holder of trusted `zhiban_runtime` credentials to issue direct child SQL without advancing parent revision. This is a trusted-infrastructure protocol boundary, not a claim that the schema enforces parent CAS against arbitrary direct SQL. RLS/composite FK still enforce their own tenant/parent boundaries. Do not add a trigger or migration in this revision; real PG16 Repository API tests must prove the protocol.
4. Compare complete persistence-relevant state. If TRUE_NO_OP, return current stored `Loaded<Membership>` unchanged; otherwise perform parent CAS `UPDATE ... WHERE tenant_id = $tenant AND membership_id = $id AND repository_revision = $expected::bigint RETURNING repository_revision`. Only rowCount 1 succeeds. Insert new grants; for existing grants, update only `revoked_at` from NULL to the first supplied timestamp. Validate affected row counts and retain all old rows. No child UPDATE for unchanged grants.
5. If the Application use case requires audit, its **transaction-bound** AuditPort appends on this same client before commit. Commit once; any failure rolls back parent revision, status, all grants, and audit together. Release the client only after known clean transaction end; destroy it if rollback/connection state is uncertain.

For `create`, insert the parent first, then explicit grants in their Domain order within one transaction, then any required audit; uniqueness/FK/RLS errors roll back all. Parent starts at revision 1 and authVersion comes from the Domain snapshot (normally 0 for `Membership.create`). No grant-only write path exists. Every child insert/revoke/replace writer first locks the parent Membership. **After** `SELECT ... FOR UPDATE` and expected-revision validation, allocate new ordinals by database-side `SELECT COALESCE(MAX(grant_ordinal), -1::bigint) + 1 FROM zhiban_identity.role_grants WHERE tenant_id = $1 AND membership_id = $2`, or strictly equivalent parameterized SQL. Empty history starts at `0`; multiple inserts receive consecutive values in approved Domain order. Keep ordinal as PostgreSQL `BIGINT`, native `BigInt`, or canonical decimal bigint string, never JS `Number`; parameterize any round-trip to pg. Signed bigint overflow fails loudly as sanitized unexpected persistence/numeric overflow; never wrap, reset to zero, or reorder history. Existing ordinals never change and gaps in a loaded history are integrity drift, not repacking. A replacement revokes old grants and appends new rows in the same transaction. RoleGrant child row shape and composite `(tenant_id,membership_id)` FK are already available in migration `0002`.

Consistent **read-only** `findById/findByUser` rehydration uses a single same-client transaction at `REPEATABLE READ READ ONLY` (set context transaction-locally before data access) so parent and child queries see one snapshot; do not assemble parent and children across pooled clients. Writer transactions remain `READ COMMITTED` with parent row lock/CAS. A single-statement consistent read is a possible later optimization, not an alternative weaker correctness contract.

## 5. Transaction roles, tenant context, and lock order

The three production contexts are distinct actual restricted logins/pools, not a superuser pool plus `SET ROLE`:

| Context | Login / scope | Work in this batch's future implementation |
| --- | --- | --- |
| `TENANT_RUNTIME` | `zhiban_runtime`; one TenantContext per transaction | Membership + RoleGrant and TENANT audit only; explicit tenant predicates and FORCE RLS |
| `AUTH_RUNTIME` | `zhiban_auth_runtime`; global but narrow | Authentication/session read/write in 1B-6, not implemented in 1B-4B |
| `CONTROL_RUNTIME` | `zhiban_control_runtime`; global, narrow | User/Tenant/SystemAdminGrant and GLOBAL control audit; no unrestricted tenant evidence read |

The `zhiban_migrator` is maintenance-only. `zhiban_identity_owner` is NOLOGIN. Neither is a runtime Repository identity. `TenantContext` is only an infrastructure scoping value; it does **not** prove authentication, User/Tenant/Membership active state, roles, permissions, or application authorization. Application must establish those before invoking a use case, and sensitive writes must re-check at their specified transaction/approval gate. The Repository checks its tenant ID matches the aggregate and sends both the explicit predicate and transaction-local `set_config('app.tenant_id', tenantId, true)` on the **same exclusive client**. `pool.query('BEGIN')` / separate `pool.query('set_config')` / separate `pool.query(data)` is forbidden. No session-level `SET app.tenant_id` or unscoped fallback.

Separate **Application validation/check sequence** from **tenant persistence transaction lock order**. Application may first obtain required global User/Tenant/operator facts through authorized CONTROL/AUTH contexts; those checks are not locks in a single cross-pool ACID transaction. Inside one TENANT_RUNTIME transaction, lock target Membership parent(s) sorted by canonical MembershipId, then relevant RoleGrant rows as writes occur, then append same-client Audit. A simple save locks its parent first and relies on that lock for child serialization when all formal writers obey the protocol. User, Tenant, and SystemAdminGrant each have their own CAS boundary. SystemAdminGrant never receives TenantContext or masquerades as a tenant RoleGrant; first `revoked_at` is irreversible. No cross-pool ACID promise, two-phase commit, superuser transaction, or `SET ROLE` workaround is implied.

**Cross-plane limit:** the verified ACL prevents `TENANT_RUNTIME` from reading/locking User or Tenant, while `CONTROL_RUNTIME` cannot act as a tenant data superuser. Thus a single unrestricted client cannot atomically lock global User/Tenant state and Membership rows under current runtime roles. 1B-4B may implement parent/child Repository atomicity, but it must **not** claim the high-risk Application authorization/approval race is solved. Do not enable activation, reactivation, role assignment, last-admin changes, or other 1B-8 high-risk flows until a separately reviewed narrow status/serialization mechanism and tests prove their transaction ordering without relaxing ACL/RLS or using migrator/owner. This is an explicit 1B-7/8 gate, not a reason to rewrite signed-off migrations in this design batch. The same distinction applies to future cross-plane User disable/session revocation composition: `CONTROL_RUNTIME` has narrow session-revocation columns, not the full SessionRepository record (including token digest). Do not reuse the latter Port as an unrestricted control-plane loader; design/test the limited atomic use case separately.

## 6. Error and retry contract

Reuse existing `IdentityPortError` class; do not add a generic error hierarchy or leak SQLSTATE/constraint text to callers. **Final Port decision for 1B-4B:** add exactly one `IdentityPortErrorCode` variant, `RETRYABLE_PERSISTENCE_FAILURE`. Keep the constructor shape `new IdentityPortError(code)` unchanged; add no `details`, `retryable` boolean, retryability field, or SQLSTATE exposed to Application. PostgreSQL `40001` (`serialization_failure`) and `40P01` (`deadlock_detected`) both map to this one code. `STALE_WRITE` remains exclusively a RepositoryRevision CAS mismatch. `UNAVAILABLE` remains for database/pool/network/connection unavailability and equivalent infrastructure faults, never these two transaction aborts. Application only needs to know that the **whole transaction** may be a candidate for explicit bounded retry after reloading/re-approval; it does not need deadlock-versus-serialization details. Infrastructure may log a sanitized internal reason, never SQL text, connection data, credentials, or raw driver detail upward. Domain constructor/privileged-rehydration errors from corrupted persisted state are sanitized to `INTEGRITY_FAILURE` at the Port boundary. A failed transaction is always rolled back; if rollback is uncertain, destroy the connection.

| Situation | Public result | Infrastructure rule |
| --- | --- | --- |
| `find` absent or RLS-invisible/wrong tenant | `null` | No unscoped existence probe; do not disclose other tenant |
| `save` absent in required scope | `CONFLICT` | Match current fake/Port convention; missing and other-tenant indistinguishable for scoped save |
| Candidate/context tenant mismatch or verified scope misuse | `TENANT_SCOPE_VIOLATION` | Reject before SQL; do not report true owner |
| Existing row, wrong expected revision | `STALE_WRITE` | Distinguish under the scoped row lock; CAS zero rows not blindly labeled stale |
| Current revision but auth-version rollback, same-version fact mutation, immutable/history violation, malformed persisted row | `INTEGRITY_FAILURE` | Entire transaction aborts; no partial child mutation |
| SQLSTATE `23505` known PK/approved unique | `CONFLICT` | Check an allowlisted constraint name; never return `detail` |
| SQLSTATE `23503` or `23514` | `INTEGRITY_FAILURE` | Scope-specific prevalidation may yield scope violation, but no generic FK existence leak |
| SQLSTATE `42501` | `UNAVAILABLE` by default | Only a verified, known RLS context rejection may become scope violation; wiring/ACL failure is infrastructure fault |
| SQLSTATE `40001` or `40P01` | `RETRYABLE_PERSISTENCE_FAILURE` | One safe Port code; no Repository automatic retry and no SQLSTATE/query/table detail exposed |
| Timeout/network/connection fault | `UNAVAILABLE` | Do not misclassify as a transaction-level retry candidate |

CAS conflicts do **not** silently replay business commands. No generic retry framework is introduced. The Repository never silently retries `40001`/`40P01`, nor re-executes a Domain command. For serialization/deadlock, any future bounded retry must be an explicit Application-level whole-transaction retry after reloading state, rechecking authorization/approval, and ensuring audit/idempotency safety; never retry only child SQL or an old Domain snapshot. Commands may carry time, approvals, audit, or external effects. A response lost after commit is not proof the operation failed; 1B-8 must decide command idempotency independently.

## 7. Row mapping and precision

Future mapper folder: `lib/zhiban/infrastructure/identity/postgres/mappers/`, one explicit mapper per aggregate and a small shared checked-scalar helper, **not** a generic ORM/change tracker. The mapper receives known, schema-qualified SELECT projections and checks exact runtime field types/nullability before constructing pure Domain state. PostgreSQL UUID strings go through `userId/tenantId/membershipId/roleGrantId/systemAdminGrantId` and `parseScope`, never `as UserId`. Unknown status, role, or scope rejects; there is no default ACTIVE/STUDENT fallback. DB `bigint` epoch-ms parses from decimal string via `BigInt`, range-checks `0..8640000000000000`, converts to JS number only after safe-integer proof, then calls `instant`. `authorization_version` likewise converts only after `0..Number.MAX_SAFE_INTEGER` proof. `repository_revision` stays a canonical positive decimal string (no global `pg` int8 parser to Number). SQL NULL maps explicitly to Domain null. No silent trimming, replacement, or truncation of persisted names/reasons. Text encoding/drift that cannot be represented losslessly fails closed. `grant_ordinal` is infrastructure-only and checked as a precise bigint/string before ordered assembly; no natural-order assumption.

Use fixed `zhiban_identity.users`, `.tenants`, `.memberships`, `.role_grants`, `.system_admin_grants`, and `.audit_events` names in SQL, never rely on `search_path` for correctness. `tenant_id`, IDs, timestamps, statuses, revision, and text are parameters. There are no dynamic table/schema identifiers. The row mapper must not write SQL snake_case into Domain objects or treat a `pg.QueryResultRow` as a Port/Domain type.

## 8. Same-transaction audit composition, without a generic Unit of Work

The existing `AuditPort.append(event)` has no transaction argument; therefore a pool-backed free-standing Audit adapter cannot prove atomicity with a Repository write. For each audited Application command, Infrastructure will create a **narrow transaction-scoped bundle**: one checked-out restricted client, one transaction, the appropriate Repository adapter bound to that client, and an AuditPort adapter bound to that **same** client. The Application calls its already-defined Ports and supplies the controlled event/actor/reason; the outer use-case composition owns commit/rollback. Bound adapters neither acquire another client nor commit themselves. Binding/lifecycle is infrastructure composition, not a `pg.Client` parameter on existing Ports and not a generic `UnitOfWork` interface.

The write use case may be exposed only through this transaction-scoped composition; a standalone repository `save` that auto-commits before audit is **not** acceptable for audited mutations. Audit failure, RLS failure, or any later validation rolls back state, children, revisions, and audit together. Conversely a Repository never decides why a Membership was disabled or creates a USER actor. Tenant audit uses TENANT_RUNTIME and same tenant context; global control audit uses CONTROL_RUNTIME. `AUTHENTICATION_REJECTED` and Session auth audit remain 1B-6. This plan does not assert that same-transaction audit is already implemented; 1B-4B/1B-8 tests must prove it. If implementation demonstrates that current Application construction cannot bind existing Ports this way, stop and propose the smallest explicit Port/composition change for review rather than silently adding a generic transaction API.
